## 0. 这份文档要什么

TUI 侧当前**不追后端漂移**（锚点冻结 + 批量适配），所以这份清单不是"要求后端适配
TUI"，而是**请求后端在既定路线里优先做几件能让 TUI 独立调测的事**。

每条都写了「阻塞了什么、期望产出、成本估计」。**P0 之外都可以谈。**

## 1. 锚点规格（P0）——"更可靠的 commit"具体指什么

> **✅ 已满足（2026-09-23）**：后端已建 annotated tag `tui-anchor-2026-09-23`
> → `5ec1900d6c937b6ff927d8f65fcd37d465de7988`（后端 `betav2`），daemon 已构建并给出
> sha256（`00642081…`，TUI 侧逐字核验相符），破坏性变更明确为"无"。
> 下表保留为**后续换锚点的验收清单**。

机主已表示会向提供锚点。以下是 TUI 侧需要的**可复现性规格**：

| # | 要求 | 理由 |
|---|---|---|
| A1 | 锚点取**集成分支**（`betav2` / `main`），不取 feature 分支 | feature 分支会继续移动；本次选 `5ec1900` 正是因为它落在后端 `betav2` 上 |
| A2 | 给**完整 40 位 SHA** | 短 SHA 有歧义；文档里的 `50d3dc1` 就是短写 |
| A3 | 该 rev **不可变**（不 force-push / 不 rebase / 不 amend） | 否则"钉 rev 才能归因"这条纪律失效 |
| A4 | 打 **tag**（如 `tui-anchor-2026-09-23`） | 引用比 SHA 可读；也防止分支被移动后找不到 |
| A5 | 该 rev 的 **daemon 能构建**，并给出构建命令 | TUI 的 PTY e2e 需要真 daemon，不只是 `cargo check` 能过 |
| A6 | 附**破坏性变更清单**（没有也要明确说"无"） | 决定 TUI 侧是"直接编译"还是"批量适配"；本次只差 2 个字段，属于最理想的情况 |
| A7 | 若可能，附一个**可运行的 daemon 产物**或固定构建配方 | 省掉 TUI 侧每次为跑 e2e 现场构建后端（18s 起） |

> 参考：上一次刷新（09-20 → `50d3dc1`）的锚点更新在 merge 时被回退，导致
> **文档写 `50d3dc1`、CI 实际钉 `66539a0`**，归因纪律实际失效了三天。
> 打 tag + 不可变承诺能直接堵掉这类问题。

## 2. 让 v2 的 PTY e2e 能覆盖 permission / ask / plan（P0）

**阻塞了什么**：v2 的 M6.3 至今没收口。`docs/report/2026-09-21-v2-m6-3-pty-hardening-report.md`
§4 自述未覆盖项：

> - permission / ask 已通过 fake provider + 真实 daemon PTY；**plan review 尚无
>   可控触发入口**；
> - …permission / ask / plan 的**真实 daemon 故障注入**未覆盖。

对应 parity 矩阵的 **P-08 / P-09 / P-10**，其中 P-10 的验收口径就写着
「lap 内挂起路径为空，**PTY 入口待补**」。

**期望产出**：一个**确定性的测试钩子**，在无真实 LLM 的前提下触发三条交互路径：

| 路径 | 现状 | 需要 |
|---|---|---|
| permission | fake provider 已可触发 ✅ | 加**故障注入**（拒绝 / 超时 / 断流） |
| ask_user | fake provider 已可触发 ✅ | 同上 |
| plan review | **无入口** ❌ | 一个可控触发（env / config / 专用命令均可） |

**为什么优先**：这是 v2 alpha 的门禁项，且是当前**唯一**卡住 v2 收口的 TUI 侧无法
自行解决的东西——TUI 不能凭空造出"后端会发 plan review"这个事实。

**成本估计**：低。fake provider 已有先例（permission/ask 就是这么做通的），
扩到 plan review 属于同一机制。

## 3. 故障注入钩子（P0）

**阻塞了什么**：TUI 的恢复路径目前只能用"杀 daemon"模拟（`scripts/e2e-v2-reconnect.sh`）。
v2 的 commit ledger 幂等、re-baseline、U-07 诊断这些**核心不变式**没有确定性的验证面。

**期望产出**：可注入的以下情形（env 开关即可，不必做通用框架）：

| 注入项 | 验证的 TUI 不变式 |
|---|---|
| SSE `lagged`（缓冲溢出终止流） | U-07 诊断文案 + 重连重定基 |
| `ringing.stream_terminated` 带稳定 code | `ReconnectReason` 渲染路径 |
| timeline **gap**（故意跳 seq） | 快照 re-baseline（禁止本地猜测历史） |
| session **404**（会话消失） | 子代理收口判据（U-29：只有 404 才映射 Closed） |
| 命令 ack **挂起/超时** | 在途命令的 UI 状态不卡死 |

**成本估计**：中低。多数是 daemon 侧已有分支上挂一个 env 判定。

## 4. 补齐 `qaqh-client` 的再导出与服务面变体（P1）

### 4.1 `ConversationInputPurpose` 未再导出

> **🔄 进行中（2026-09-23）**：后端已基于 `betav2` 单开 PR **#289**
> （head `d60adea`，open / 未 merge），只做该 re-export + 一个公开 API 编译回归测试，
> 不再挂在大 PR 上。TUI 侧**不锚 feature head**，等 merge 后后端新开
> `tui-anchor-2026-09-23-r2` 再升锚点（旧 tag 不移动）。

`qaqh-client/src/types.rs` 开头自述：

> 再导出的完整性是**有意的**：壳层只认 `qaqh-client` 一个入口，不该越过它去直接依赖
> `qaqh-domain`/`qaqh-ringing`/`qaqh-types`。**缺一个名字，壳层就只能再抄一份镜像**
> ——而抄镜像正是漂移的来源。

但 `ConversationInputPurpose`（`45c6b63` 新增）**没有进再导出列表**。后果：TUI 无法命名
该类型，只能写 `input_purpose: Default::default()`（见 `src/app/transcript_ops.rs`），
也就无法表达 `QueueOnly`。

**期望**：加进 `pub use qaqh_domain::{…}`。

### 4.2 服务面 typed 变体缺口（台账 U-14）

daemon 的服务表与 `service.rs` 已有这些方法，但 `qaqh-client` 的
`QueryRequest`/`ActionRequest` 枚举**没有对应变体**，TUI 因此调不到：

```
session.meta · plan.read · plan.context_stats · stats.token_usage · git.*
```

**期望**：补变体；或者明确回答"TUI 永久不需要这几个"，TUI 侧好销账（当前状态是
`DECIDE`，挂着没人能推）。

### 4.3 测试专用开关集中登记

TUI 的 e2e 已经在依赖 `QAQH_TEST_LEASE_TTL_MS`（W-04 租约自愈 harness）。
**期望**：一份"测试专用环境变量 / 开关"清单（名字、语义、是否承诺稳定），
避免每个 harness 都要考古源码。

## 5. 为 P3 / P5 各留一次"变更交底"（P2）

### 5.1 P3：typed todo 的消费路径

后端 P3 活跃分支（`be7ad6f`）**已删除 `qaqh-client::TodoItem`**，而 TUI 的
`src/app/session.rs` 仍在用它渲染 workspace todo 列表。

**期望**：P3 落地时说明 TUI 应该改读哪个类型（`TodoItemView`？`qaqh-workspace` 的
`todo/model.rs`？），以及旧 `TodoItem` 的字段对应关系。

**为什么重要**：这决定 TUI 那处是"换个类型名"还是"换一整套数据面"——工作量差一个量级。

### 5.2 P5：协议大改的 wire 级说明

机主已确认 **P5 起是前后端协议大改**。TUI 侧需要据此排期。

**期望**（P5 开工前）：
1. wire 级变更说明：哪些频道 / 事件 / 命令 / 字段变化；
2. 是否保留兼容层、保留多久；
3. 大致时间点。

**为什么重要**：TUI 侧的 `v1/v2 parity matrix` 与终端兼容矩阵**都是在旧协议上验的**。
若 P5 早于 v2 alpha 落地，这两套矩阵要在两套协议上各验一遍——所以 TUI 希望
**v2 alpha 尽量赶在 P5 之前**。这个排期只有在拿到 P5 时间点后才能定。

## 6. 明确**不需要**后端做的事

写清楚是为了避免这份清单被读成"TUI 要求后端改协议"：

- ❌ 不需要为 TUI 的视觉/交互改协议或加字段（v2 计划 §4.5 已冻结：**v2 不依赖后端新字段**）；
- ❌ 不需要为 TUI 加"UI 专用"的旁路接口；
- ❌ 不需要保证旧 rev 永远可编译——TUI 侧用**钉 rev** 解决（CI + 本机锚点机制）；
- ❌ 不需要为 TUI 的进度放慢 P3/P5。
