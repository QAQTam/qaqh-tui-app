## 0. 一句话结论

**TUI 当前为了展示工具结果，写了 268 行 JSON 解析代码，因为后端把结构化数据塞进了
`summary` / `output` 字符串。** 只要后端把展示投影类型化（header / body / metrics），
这 268 行可以全部删除。

## 2. 量化：86.4% 的 summary 是原始 JSON

真实会话 `5e34cca4`（2500 次工具调用）实测：

|---|---|---|---|
| **exec** | 1907 | **1900（99.6%）** | 460 B |
| read | 312 | 0 | 47 B |
| edit | 116 | 110（94.8%） | 80 B |
| todo_update | 65 | 65（100%） | 318 B |

典型样本（TUI 直接拿到的东西）：

```
[exec]        {"status":"completed","command":"bash ...","exit_code":0,"output":"总计 79764\\ndrwxr-xr-x ...
[todo_write]  {"timeis":"UTC+8 ...","status":"ok","replaced":0,"total":3,"assigned":["T1","T2","T3"],...
```

这些字符串**被 `TOOL_SUMMARY_MAX_CHARS` 从中间截断**，连 JSON 都不合法，无法解析。

## 4. 逐工具的消费需求

### 4.1 exec / bash / pwsh（76% 调用量，最高优先级）

**TUI 现在做**（L1898-2010）：从 `output` JSON 剥壳取正文、从 JSON 抠 `exit_code`、
判断 `truncated`、Running 时用 `progress` 作流式预览、终态时优先用剥壳后的 output。

**TUI 需要**：

| 需求 | 用途 | 优先级 |
|---|---|---|
| `stdout` / `stderr` 或合流 `output` | 正文渲染 | P0 |
| `exit_code: Option<i32>` | 状态图标（✓/✗）+ 标题行 | P0 |
| `truncated: bool` | 「已截断」提示（对齐 B1「丢弃必须可见」） | P0 |
| `command: String` | 标题行显示完整命令 | P0 |
| `user_initiated: bool` | 用户 `!` 命令默认展开、截断行数放宽 | P1 |
| `elapsed_ms` | **当前完全没有耗时显示** | P2 |

**注意**：TUI 侧还有一个 `apply_bash_progress`（`timeline_model.rs:82`，约 60 行）
在处理 `\r` 覆盖语义与 ANSI 剥离。若后端在 `ToolBody::Shell.stdout` 里给
**已归一化**的文本，这部分也可简化。

### 4.2 read / write / edit / apply_patch / glob（文件类）

**TUI 需要**：`path` + 操作类型（读/写/改/列/删）。
现状靠 `extract_path(args_json)` 抠 path（L1098）。

`edit` / `apply_patch` / `write` 的 diff 已在独立字段 `tool.diff`，**这块是好的**，
不需要改。

### 4.3 grep / web_search / web_fetch（检索类）

**TUI 需要**：`query` + 可选 `scope`（路径/URL）。
现状 grep 的 summary 已是人类可读（"path resolves outside the workspace"），
说明**后端有能力产出好 summary**，只是 exec 等工具没走这条路。

### 4.4 todo_write / todo_update / todo_list（专属面板，100% JSON）

这三个工具 TUI 已判为 `is_panel_owned_tool`（L1132），**不渲染输出体**，
只在标题行给状态（`panel_owned_note`）。但它们的 summary 是 100% JSON，
连状态都无法直接读。

**TUI 需要**：结构化 items（id / title / status / evidence），
或者至少一个 canonical 的人类可读 summary（如 "Plan updated: 3 items (3 new)"）。

**待确认**（对应后端 spec Q9）：TUI 是否要引入 `ToolBody::Table` 来渲染
todo 面板？当前设计是「专属面板工具不渲染输出体」，若保持该设计，
则只需 canonical summary，不需要 `Table`。

### 4.5 ask / skills / spawn_subagent

同 todo 系列，`is_panel_owned_tool` 成员，只需 canonical summary。

### 4.6 process / journal / 其它结构化工具

现状走 `pretty_json_output` 兜底（L1187）：能美化就美化，否则原样透出。
**这是「信息零丢失」的正确兜底**，后端 spec §4.5 要求保留同等兜底。

## 5. TUI 侧契约需求汇总

按后端 spec §4 的结构对应：

| TUI 需求 | 后端字段 | 优先级 | 受益面 |
|---|---|---|---|
| shell 结构化正文 | `ToolBody::Shell { stdout, stderr, exit_code, truncated }` | **P0** | exec 76% 调用 |
| summary 禁 JSON | 规则 H11 | **P0** | 86.4% 调用 |
| 命令/path 语义 | `ToolHeader::{Shell, Path, Query}` | P1 | 删 `extract_path`/`exec_command_summary` |
| todo 结构化或 canonical summary | `ToolBody::Table` 或 canonical summary | P1 | todo 100% JSON |
| 耗时 | `ToolMetrics.elapsed_ms` | P2 | 新增能力（当前无） |
| 是否用户发起 | `ToolMetrics.user_initiated` | P2 | 展开/截断策略 |
| 流标识（stdout/stderr） | 后端 spec §5 | P2 | 现在合流显示，可接受 |

## 6. TUI 侧不需要的（避免后端过度设计）

- **不需要** `stdout` / `stderr` 分开存储（合流即可，对齐 Codex UI 侧 `aggregated_output`）。
- **不需要** 工具原始 `value` JSON（那是宿主/审计的事，TUI 永不读）。
- **不需要** 模型投影串（`formatted_output` 类）——Codex 的 TUI 也从不消费它。
- **不需要** `progress_truncated`（当前就是死字段，可删或由 `body.truncated` 取代）。

## 7. 迁移后 TUI 的预期状态

- 删除 §3 的 8 个函数（约 268 行）+ 6 处 `serde_json::from_str`。
- `push_tool_card` 按 `ToolBody` / `ToolHeader` 变体分派，去掉字符串匹配。
- `apply_bash_progress` 若后端归一化则可简化。
- 新增耗时显示（当前完全没有）。
- 新增 `user_initiated` 驱动的展开策略。

## 8. 验收（TUI 侧）

- `src/app/render_transcript.rs` 中工具展示路径的 `serde_json::from_str` 调用数为 **0**。
- 滚动长会话（≥100 回合）时 exec 卡片标题显示完整命令、状态图标与 exit_code 一致。
- `cargo test` 全绿；渲染相关快照测试更新。
