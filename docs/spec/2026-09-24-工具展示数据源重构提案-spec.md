> 面向后端。本文在 TUI 仓 `docs/spec/2026-09-24-工具展示数据源重构提案-spec.md`
> 与后端 issue 各存一份，**讨论与决议以后端 issue 为准**。
> 本文只讲**展示面数据从哪来**，不推翻既有的
> `docs/spec/2026-09-18-工具结果展示契约-v1-spec.md`（Phase A–E 已完成大半），
> 是在它之上补一层**内容契约**。

## 1. 问题：摘要是"输出首行"，不是"为展示构造的一句"

现状（`qaqh-workspace/src/file_mutate.rs::mutation_display`）：

```rust
let (text, truncated) = clamp_display_body(output);
let mut display = ToolDisplay::new(header, ToolBody::Text { text, truncated });
display.summary = first_line(output);   // ← 摘要 = 给人看的输出文本首行
```

于是同一个字段在不同工具下**来源不同、含义不同**，真机实拍：

| 工具 | 摘要（= 输出首行） | 撞上的重复 |
|---|---|---|
| `edit` | `[OK] edit a.rs` | 自带工具名 → 卡片名再前缀一次 → `edit [OK] edit a.rs` |
| `write` | `[OK] /path — 16 bytes, 1 lines (new file)` | 自带 `[OK]` → 与状态行 `✓ done` 重复 |
| `read` | 文件内容首行 | **必然**与正文首行逐字重复 |

三条都不是"没迁移"（投影确实注册了、header 也是 typed 的 `ToolHeader::Path`），
而是**没人规定 `display.summary` 该长什么样**：§7.1 只定了来源优先级与"不许是
JSON"，没定内容。TUI 侧因此被迫加启发式（从文本里认 `[OK]`、去掉开头的工具名）
——**这是契约缺口在下游的必然代价**。

## 2. 四家怎么做（本地源码核对）

| | 模型面 | 展示面 | 终态怎么表达 |
|---|---|---|---|
| **Gemini CLI** | `ToolResult.llmContent` | `ToolResult.returnDisplay`：**判别联合** `string \| FileDiff \| AnsiOutput \| TodoList \| SubagentProgress \| GrepResult \| ListDirectoryResult \| ReadManyFilesResult` | `error?: { message, type: ToolErrorType }` **独立字段** |
| **opencode** | `ToolStateCompleted.content`（typed `Content[]`） | `ToolStateCompleted.metadata: Record<string, Json>`（工具自填的展示扩展点） | `ToolState` 是**判别联合**：`streaming \| running \| completed \| error`（status 是 tag，不是文本） |
| **Grok CLI** | `ToolOutputWire = Text \| Json \| Mcp{blocks}` | 独立的 `xai-grok-pager-render` crate 消费 typed 工具定义（read.rs/grep.rs/glob.rs… 输入输出都是 struct） | `ToolCallResult` 带 `follow_ups` / `reminders` 等结构化附属 |
| **Codex CLI** | `ExecToolCallOutput` | TUI `exec_cell` 从**结构化事件**渲染 | `exit_code` / `timed_out` / `duration` / `stdout` / `stderr` **全是字段**，且 stdout 与 stderr 分开 |
| **我们（qaqh）** | `output`（文本） | `display.summary = first_line(output)` | 结构化 `state` 与文本里的 `[OK]` **并存** |

共同点只有一条，但四家都守着它：

> **展示所需的信息是结构化的、由工具自己产出的，不是从"给人看的文本"里回捞的。**

Gemini CLI 的源码注释甚至自承这层是 UI 关切：

> `returnDisplay` … NOTE: This might also be considered UI-specific and could
> potentially be removed or modified in a further refactor if the server becomes
> purely API-driven.

也就是说：**"展示数据该由谁产" 是有取舍的，但"展示数据不该从展示文本里回捞"
没有争议。**

## 3. 提案（三步，可按序独立落地）

### P1 — 内容契约（零 wire 变更，可立即做）

规定 `display.summary` 是**为展示面单独构造的一句**，并给出三条硬约束：

1. **不含工具名** —— 名字由卡片的 `name`（或 `header`）承担；
2. **不含终态标记** —— 终态由结构化 `state` 承担；
3. **不得等于 `output` 的首行** —— 没有更好的摘要时宁可 `None`，让 client 只画
   `header`（TUI 现在能正确处理 summary 缺失）。

具体到文件工具族：`write` / `edit` / `apply_patch` 的摘要应退化为**元信息**
（如 `a.rs · +3 −1`），`read` 退化为 `path · L1-L40` 或直接 `None`。

**收益**：`edit [OK] edit a.rs` 与 `read` 的重复当场消失，不需要 wire 变更。
**代价**：TUI 侧会短暂出现"两种风格"（旧 client 无所谓；新 TUI 已兼容两种）。

### P2 — 结构化终态（小 wire 变更，建议并入 Phase E → v2）

`ToolDisplay` 增加 `outcome` 子结构（等价于 Codex 的 `ExecToolCallOutput`）：

```rust
pub struct ToolOutcome {
    pub state: ToolTerminalState,      // succeeded | failed | cancelled | timed_out
    pub exit_code: Option<i32>,
    pub duration_ms: Option<u64>,
    pub output_bytes: Option<u64>,
    pub truncated: Option<bool>,
}
```

`display.metrics` 已有 `elapsed_ms` / `output_bytes`，本步主要是把
**state / exit_code / timed_out** 从文本搬进结构。

**收益**：TUI 可以删掉"从 summary 文本里认 `[OK]`"的启发式
（TUI 侧 `marker_states_success`，本轮临时加的），终态只有一个真相源。
**这是当前重复的**根**：`[OK]`（文本）与 `state`（结构）是同一事实的两套表示。**

### P3 — stdout / stderr 分离（v2）

`ToolBody::Text { text }` 拆成 `ToolBody::Streams { stdout, stderr, interleaved: bool }`
（Codex 与 Grok 都这么做）。spec D2 已经把它列为"真实交织顺序延后 v2（需 pipe 层
序号）"——本提案不催，只是登记它是 P2 的自然延续。

## 4. 与既有计划的关系

- **不推翻** Phase A–E：P1 属于"内容契约"，是 §7.1 缺的那半页；
- **P2/P3 落在 Phase E → v2 收紧窗口**（spec 决策 D10 已写明"旧字段不早于
  Phase E 删除"）；
- 既有验收口径（`serde_json::from_str` 8→0、typed display 优先）**不受影响**，
  本提案只加不改。

## 5. 验收（可测）

- P1：文件工具族的 `display.summary` 与 `first_line(output)` **不再相等**；
  单测直接断言 `read`/`write`/`edit` 三条（现在的测试断言的正是相等，要改）。
- P2：TUI 侧删除 `marker_states_success` 后，`⚙ edit [OK] …` 的重复不回归
  （由 TUI 的 `tool_card_does_not_repeat_what_summary_already_says` 覆盖）。
- P3：同一命令的 stdout/stderr 在卡片里可分辨（Grok/Codex 均有先例可对拍）。

## 6. 跨仓承诺（TUI 侧）

| 后端落地 | TUI 随之删除 |
|---|---|
| P1 | 头部"以工具名开头就不前缀"的启发式（`strip_tool_prefix`） |
| P2 | `marker_states_success`（从文本认 `[OK]`） |
| P3 | 无（新增能力） |
