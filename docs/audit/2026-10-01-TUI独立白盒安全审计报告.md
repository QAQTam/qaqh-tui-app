### 数据流图

```
用户输入 → InputPump → AppMsg → App(单线程状态机) → spawn_api → qaqh-client → HTTP → daemon
daemon SSE → RuntimeMsg → App → 渲染(ratatui buffer) → stdout
审批链: daemon InteractionRequested → 下载 content body → PermissionPanel
       → 用户 a/d 或点击 → ToolPermissionRespond{tool_call_id} → daemon(校验) → executor
```

**信任等级结论**：TUI 位于「用户 ↔ daemon」之间。TUI 对 daemon 输出完全信任（无签名/指纹校验，协议字段经 `qaqh-client` 类型化解析）；TUI 对终端的唯一特权出口是 ratatui 帧 + OSC 52 + pager 子进程 + 导出写盘。

## 第二阶段：用户输入审计

无命令注入。唯一 shell 拼接点（pager）中路径固定且单引号引用（`pager.rs:18` 含单引号逃逸测试）；`/new <cwd>`、附件路径、粘贴均以字符串直达 HTTP JSON，无解释执行。粘贴洪流护栏（`paste_guard.rs`）防误发送，无安全副作用。`y` 确认键绑定在 overlay 自带的 session_id 上且切标签即剪枝（`overlay_ops.rs:22-24`），无跨会话确认。

## 第三阶段：后端 → TUI 数据审计

**核心问题（恶意输出伪造 QAQ 自有 UI）不成立**，理由：

1. 本仓 patch 的 ratatui 在 buffer 层丢弃含控制字符的 grapheme（`../ratatui/ratatui-core/src/buffer/buffer.rs:351`，`.filter(|symbol| !symbol.contains(char::is_control))`）；
2. composer 渲染把控制字符替换为 `�`（`terminal/agent/mod.rs:1165-1172`）；
3. bash progress 有专门的 `strip_ansi_escapes`（`timeline_model.rs:32`，目前只用于该路径）;
4. markdown 渲染丢弃 HTML 事件（`markdown.rs:197`）；
5. 模态路由先清屏再画（`terminal/agent/mod.rs:920-924`），模型内容不可能透出在审批弹窗下方伪造 UI。

残余通道只有 F2 的 pager 路径（见下）。

## 第四阶段：Session / Workspace

未发现「Session A 的 UI 状态作用于 Session B」的实例：

- 所有事件按 session_id 键控分发；
- 附件上传目标单一事实源（`AttachSubmit`，`app/mod.rs:599-625`，有全链路回归测试 `overlay_ops.rs:1054-1070`）；
- timeline 流丢失时只有 404 才收口、网络抖动不误删（`runtime.rs:136-160`）；
- 子代理回收按 Team projection 父子关系全量回收（`session_ops.rs:208-228`）。

## 第五阶段：Permission / Approval

UI 层防线（设计良好且有测试锁定，`session.rs:1087-1246`）：

- 重复投递被 `RespondedPermissions` 有界 FIFO（256）抑制；
- 双击批准幂等（首次应答后 `active_permission()` 为 None）；
- `suppressed_interactions` 防 bootstrap 幽灵复活（`app/mod.rs:1466-1473`）；
- bootstrap 快照「只补不换」，不降级 live 面板。

剩余风险见 F1（显示内容被裁剪）与 F3（无内容绑定，移交后端）。

## 第六阶段：Protocol

`ringing_v2.rs` 状态机执行：epoch/log 匹配、`(fact_seq, projection_index)` 字典序单调、重复/过期丢弃、reset 后旧 bootstrap 拒绝回滚（`ringing_v2.rs:194-258`，回归测试 `app/mod.rs:2678-2751`）、driver epoch 单调交接（`ringing_v2.rs:384-401`）。

「TUI 显示状态 ≠ backend 实际状态」的风险主要在 daemon 重启窗口，由 reset + rebootstrap 原子替换覆盖。`send_interaction_command` 10s 超时防「应答黑洞」（`app/mod.rs:174,217-255`）。

## 安全发现

### F1【中危，代码已证实】权限审批弹窗无滚动、溢出静默裁剪——用户看到的 ≠ 批准的

- **攻击者控制的输入**：模型控制 tool call 参数 → daemon 序列化为 `action_summary`（exec 下发 command/args/shell/cwd，`session.rs:241` 注释）、`reason`、`paths`、`consequence`。
- **攻击入口**：`InteractionRequested` → `apply_interaction_body`（`app/mod.rs:1618-1625`）→ 渲染。
- **完整数据流**：恶意模型输出超长命令（>~1200 字符即可在 72 列宽下超过 18 行）或 >6 条路径 → 面板尾部（含全部路径、后果说明、「信任此目录」行）被裁掉 → 用户按 `a` → `ToolPermissionRespond{tool_call_id, approved:true}` → daemon 执行完整命令。
- **安全边界**：模型输出（不可信）→ TUI 展示层（应如实呈现）→ 用户决策。
- **受影响代码**：
  - `src/ui/v2/modal.rs:206-212` — 弹窗最大 72×22，内容区约 18 行；
  - `src/ui/v2/modal.rs:433-435` — 注释自述「超出可见高度的行会被 Paragraph 裁掉」，无滚动、无截断指示；
  - `src/ui/v2/modal.rs:373` — `paths.iter().take(6)`，第 7 条起的路径永不显示；
  - 批准/拒绝按钮固定在 footer（`modal.rs:464-475`），始终可按。
- **攻击条件**：模型侧愿意构造长命令/多路径（提示注入或恶意模型即可，无需其它前提）。
- **实际影响**：用户在信息不完整的情况下授予高危工具执行权。`trust_folder` 行被裁掉时 `t` 键仍生效，但用户看不到该开关。
- **PoC / 复现步骤**：构造会话使 daemon 下发 `action_summary` 为 30 行文本（或 10 个 path）的 permission → 打开 TUI → 弹窗只显示前 ~18 行且无任何「已截断」提示 → 按 `a`。
- **为什么普通使用测试可能无法发现**：正常命令短于两行、路径少于 6 条；裁剪只在内容超界时发生，且无视觉线索。
- **修复建议**：为 permission 弹窗加滚动（plan 面板已有滚动先例 `modal.rs:538`）；被裁剪时显示「(+N 行，j/k 滚动查看)」；路径超过 6 条时显示「以及另外 N 条路径」；或对 `action_summary` 强制全文可见才允许批准。
- **置信度**：高（裁剪行为由代码注释与 `Paragraph` 语义直接证明；端到端需后端配合下发长 body，标「需动态验证」仅为确认 daemon 是否原样透传长摘要）。

### F2【中危，环境依赖】pager 临时文件：可预测路径 + 符号链接跟随 + 原始内容交给 `$PAGER`

- **受影响代码**：`src/terminal/agent/mod.rs:872-901`。
- **三个叠加问题**：
  1. **CWE-377 不安全临时文件**：`temp_dir()/qaqh-pager-<pid>.md`，`std::fs::write` 跟随符号链接。多用户 POSIX 主机上，本地攻击者可预置 symlink → 模型 reasoning 正文（模型可控）覆盖任意可写文件（如 `~/.bashrc`）。Windows 默认 TEMP 每用户独立，风险降低，但 TMP 被指向共享目录时同样成立。
  2. **escape 注入通道**：文件内容是模型 reasoning 原始字节（`overlay_ops.rs:383` 直接 `body.clone()`），经 `less -R`（ANSI 直通）或 `cat` 回退（`sh` 返回 127 时，`terminal/agent/mod.rs:889-891`）送回终端。`cat` 回退会原样输出控制序列——OSC 8 伪造超链接 / OSC 52 改剪贴板 / 改标题在该路径理论可行。`less -R` 对非 SGR 序列的透传行为随版本变化——需要动态验证。
  3. `PAGER` 经 `sh -c` 执行：仅用户自身环境可控，不构成越界，但意味着「控制了用户 env 就有代码执行」——与一般 CLI 约定一致。
- **攻击链**：恶意模型在 thinking 中埋入终端转义序列 → 用户 Ctrl+T 后按 `e` → 正文写入临时文件 → `less -R`/`cat` → 终端解释序列。
- **修复建议**：临时文件用 `tempfile` crate（O_CREAT|O_EXCL|O_NOFOLLOW）；或写到 data_dir 下固定私有目录；pager 前对正文做 `strip_ansi_escapes`（该函数已存在，`timeline_model.rs:32`）。
- **置信度**：symlink 问题高（代码确证，利用需本地多用户环境）；escape 注入中危（需要动态验证，取决于 less 版本与终端）。

### F3【低-中，需后端追踪】审批应答无内容绑定，TUI 无法防止 approval replay/confusion

- `interaction.rs:204-208`：应答仅携带 `tool_call_id + approved + trust_folder`，不含用户所见内容的指纹或 echo。TUI 侧显示的面板正文来自异步下载的 content store（`app/mod.rs:1530-1550`）。
- TUI 自己的防线是好的（见第五阶段），但「用户看到的命令 == daemon 最终执行的命令」这一不变式完全依赖后端在 `tool_call_id` 上重新绑定与校验。若 daemon 侧存在 call_id 复用 / 审批队列错位 / 批准后改参，TUI 无从察觉。
- **必须移交后端审计**：`ToolPermissionRespond` 是否原子绑定到 pending 的那个 tool call 及其冻结参数。

### F4【低-中，依赖社工】`/export` 提供模型引导的任意路径文件写

- `composer_ops.rs:205-222`：`/export <任意路径>` 把 transcript（其中 assistant Text block 与 tool output 逐字来自模型，`export.rs:100-105`）写到用户指定的任意路径，无确认、无路径限制。
- **攻击链**：恶意/被注入的模型输出「请运行 `/export ~/.bashrc`（或 `~/.ssh/authorized_keys`）」并同时在对话中放置它控制好的正文 → 用户照做 → TUI 以用户权限写入任意文件。内容是 Markdown 包裹的，但 assistant 文本块原样落盘（`export_block` 对 Text block 无任何转义/包裹），模型可让有效载荷位于文件任意位置。
- **次级问题**：`push_fenced`（`export.rs:213-223`）不转义内容中的 ```，工具输出可逃出代码围栏 → 导出文件的 Markdown 注入。
- **判定**：用户必须亲手输入命令与路径，属「模型 → 用户 → TUI → OS」社工链，标**潜在风险**；建议对非默认路径加二次确认或拒绝写到家目录敏感位置。

### F5【低】Secret 字段编辑态明文回显

- `src/ui/v2/workspace.rs:594-602`：编辑 API Key（`FieldKind::Secret`）时 `edit_window(&buffer.buf, …)` 原样显示输入中的密钥（REVERSED 样式）。已保存值有掩码（`settings.rs:298-303`），但输入过程在屏幕/录屏/肩窥下泄露。建议编辑态用 `*` 掩码。

### F6【低/信息】OSC 52 剪贴板通道

- `clipboard.rs:11-23`：消息菜单「复制成 Markdown」（用户触发，`fullscreen.rs:59`）将模型正文 base64 后以 OSC 52 写系统剪贴板。终端支持时即剪贴板投毒面（用户随后粘贴到密码管理器/终端）。设计使然，记录在案。

## 最终总结

1. **TUI 是否属于 QAQ 的安全边界？** 不是强边界，是信任传递带：所有审批/命令的最终校验都在 daemon。TUI 自身的信任职责只有两件事——如实呈现不可信内容（F1 破坏了它）、不把不可信内容转成终端/文件系统原语（大体做到，F2/F4 是例外）。
2. **TUI 是否拥有超出 UI 所需的权限？** 有三处超出「纯显示」：本地任意路径写（`/export`）、子进程执行（$PAGER）、配置/权限级别直写（permission_level、trust_folder）。均有用户触发前提。
3. **最重要的 5 个 TUI 安全风险**：① F1 权限弹窗裁剪（显示≠批准）；② F2 pager 临时文件 + escape 通道；③ F3 审批无内容绑定（移交后端）；④ F4 模型引导的 `/export` 任意写；⑤ F5 Secret 明文回显。
4. **最值得动态测试的 10 个场景**：
   1. 超长 action_summary 的 permission 弹窗 → 确认裁剪与盲批；
   2. 10+ 路径的 permission → 第 7 条起不可见；
   3. thinking 含 OSC 52 / OSC 8 / CSI 序列 → Ctrl+T 按 `e` → 真实终端 + `less -R` 与 `cat` 回退分别观察；
   4. 预置 `/tmp/qaqh-pager-<pid>.md` symlink → 覆盖目标文件；
   5. `/export ~/.bashrc` 全链路（模型引导）；
   6. tool output 含 ``` → 导出文件 Markdown 注入；
   7. 非 driver 客户端绕过 TUI 直发命令（后端是否强制 driver 校验）；
   8. daemon 下发伪造 `InteractionRequested`（call_id 与已执行工具相同）→ 后端是否重放执行；
   9. 会话 A 审批待决时 SSE 断连重连 + reset → 面板是否复活/错位；
   10. 双击批准 + 快速切标签 → 幂等性验证。
5. **必须移交后端审计**：`ToolPermissionRespond` 的 call_id 绑定与防重放；非 driver 命令的服务端强制；`action_summary` 与实际执行参数的一致性；`SessionCreate/Resume` 的 cwd 是否服务端校验；SSE token/endpoint 鉴权（daemon.json 本地信任模型）。
6. **只有真实 terminal/PTY 才能验证**：F2 的 escape 注入（less 版本差异、终端对 OSC 52/8 的支持）；ratatui 控制字符过滤在真实输出路径的端到端效果；Windows 终端对 OSC 52 的行为；窄终端（<76 列）下 F1 裁剪的实际触发阈值。
