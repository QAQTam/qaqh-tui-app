## 3. 发现 D-1：renew 的 plain 401 被判为致命，supervisor 永久退出

### 3.1 现象

流式输出期间前端 SSE 报错后，TUI 停在 `✗ lost` 且后续请求一律 401，**无法恢复**，只能重启进程。

### 3.2 根因（E1 + E2）

daemon 对三种失败都返回 401，其中两种 body 是 **plain text**：

```
$ curl -s -i -X POST http://127.0.0.1:52689/ringing/v1/leases/renew \
    -H "Authorization: Bearer $TOKEN" -H "x-qaqh-client-session-id: deadbeef"
HTTP/1.1 401 Unauthorized
content-type: text/plain; charset=utf-8
content-length: 24

lease expired or unknown
```

（token 错时同样是 plain text，body 为 `unauthorized`，`auth.rs:12`；JSON 形态仅 `lease_required`。）

修前的 `classify` 只区分「JSON → LeaseRequired」与「其它 401 → Unauthorized」：

```rust
// src/transport/http.rs:132-140（修前）
if status == reqwest::StatusCode::UNAUTHORIZED {
    if let Ok(err) = serde_json::from_str::<WireError>(&text) {
        if err.code == "lease_required" { return Err(ApiError::LeaseRequired(err.message)); }
        return Err(ApiError::LeaseRequired(err.code));
    }
    return Err(ApiError::Unauthorized);   // ← "lease expired or unknown" 落这里
}
```

而 supervisor 把 `Unauthorized` 当不可恢复错误：

```rust
// src/runtime.rs:201-204（修前）
Err(e) if e.is_unauthorized() => {
    let _ = msg_tx.send(RuntimeMsg::Conn(ConnEvent::Lost(e.to_string())));
    return;          // ← supervisor 任务永久退出
}
```

于是「租约过期」（本可通过重新 open 换新租约自愈）被当成「token 错」（不可恢复），连接生命周期任务直接终结。三条频道流仍持旧 `client_session_id` 死循环重连 → daemon 回 401 `lease_required` → 界面永久 `✗ lost`。

对照复用路径 `qaqh-client/src/session.rs:224-229`：只判 `!is_success()` → 累加失败计数 → 连续 2 次即 `open()` 重新协商，**从不把任何 401 当致命**。

### 3.3 影响面

所有 TUI 用户；触发条件为「daemon 端租约过期」——流式输出期间事件量大、daemon 侧锁竞争或停顿（如 `renew` 被拖过 30s TTL）即可造成，与用户观察到的「流式输出时」高度吻合。

### 3.4 复现（E1）

```bash
# 1) 取当前 daemon 凭据
TOKEN=$(python -c "import json,os;print(json.load(open(os.path.expanduser('~/.qaqh/daemon.json')))['token'])")

# 2) 用一个不存在的 session 触发 renew（等价于租约已过期）
curl -s -i -X POST http://127.0.0.1:52689/ringing/v1/leases/renew \
  -H "Authorization: Bearer $TOKEN" -H "x-qaqh-client-session-id: deadbeef"
# 期望：401 + plain "lease expired or unknown"  ← 修前会被判为 Unauthorized
```

### 3.5 修复建议（已实施）

1. `classify` 按 **body 内容**区分三态（`http.rs:174-184`）：JSON → `LeaseRequired`；plain `unauthorized` → `Unauthorized`；其余 plain 401 → `LeaseRequired`（携带原文便于诊断）。
2. 新增 `is_fatal()`（仅协议代差）与 `is_credential()`（token/租约）语义（`http.rs:63`、`:68`），替换原先三个易误用的判定方法。
3. supervisor 决策抽为纯函数 `supervisor_action()`（`runtime.rs:176`），**只有 `is_fatal()` 才能产出 `Stop`**，并加防回归测试。

### 3.6 验收清单

```bash

cargo test runtime::tests::lease_expiry_must_reconnect_not_stop

# 期望：全部 ok；且第三个测试对 5 种非致命错误 × 3 档失败计数均断言 != Stop
```

## 4. 发现 D-2：daemon 重启后凭据不刷新

### 4.1 现象

daemon 重启（换端口/token）后 TUI 持续 401，不自行恢复。

### 4.2 根因（E2）

daemon 启动时随机生成 token 写入 `daemon.json`（`server.rs:119`：`config.token.clone().unwrap_or_else(random_hex)`）。修前 `HttpClient` 的 `base_url` / `token` 是不可变 `String`，仅在 TUI 启动时读一次 discovery（`main.rs:56-61`）——运行期**从不重读**（`rg "daemon.json"` 仅命中 `discovery.rs` 与 `main.rs` 的 doctor 分支）。

### 4.3 修复（已实施）

- `base_url` / `token` 改为 `RwLock`，新增 `apply_discovery()` 原地换值（`http.rs:110`）。
- `refresh_credentials()`（`runtime.rs:193`）重读 `daemon.json` 并热更新；在 supervisor 启动时、每次 open/renew 凭据类失败时、以及流任务连接失败时调用。
- 读取 token 时先 clone 出锁（`http.rs:144` 的 `fn token()`），避免 `RwLockReadGuard` 跨 `await` 使 future 变成 `!Send`（该编译错误已在本轮实测触发并修复）。

### 4.4 验收清单

```bash
cargo test transport::http::tests::apply_discovery_hot_swaps_credentials
# 期望 ok：换值返回 true，base_url 去掉尾斜杠，token 生效
```

## 5. 发现 D-3：同 epoch 重协商不触发流重连（伪健康黑障）

### 5.1 根因（E2）

`ConnInfo.generation` 在 `runtime.rs:180`（修前）递增并写入 watch，但**全仓无人读取**。两条流任务只比较 `epoch`：

```rust
// src/runtime.rs:340（修前）
if conn_rx.borrow().epoch != epoch { cursor = 0; reconnect = true; }
```

而 daemon 租约过期后重新 open 时 **epoch 不变**（epoch 仅在 daemon 进程重启时更换，`server.rs:124`）。旧流因此既不重连也不归零，继续持失效的 `client_session_id`——服务端 `is_active_session` 为假、不再投递任何事件，客户端状态却仍显示 `ready`。

`qaqh-client` 为此专门用 `session_ctx` watch 广播新 `(epoch, client_session_id)`，并在流循环里监听变化后主动断开（`sse.rs:132-146`，注释直指该黑障）。

### 5.2 修复（已实施）

两条流任务各记录 `known_generation`（`runtime.rs:408`、`:579`），在 `conn_rx.changed()` 分支同时比较 epoch 与 generation；generation 变化即重连（同 epoch 内 cursor 保留续传，epoch 变化才归零）。

### 5.3 验收清单

`cargo test runtime::` 全绿；人工验证：daemon 重启后 TUI 应显示「已重读 daemon 记录，重新协商」并自动恢复，无需重启进程。

## 6. 发现 D-4：缺 `ringing.stream_terminated` 归一

### 6.1 根因（E2）

daemon 在 live 广播 `Lagged`（事件环溢出）时发终止帧并**立即关流**（`sse.rs:356-374`）。TUI 全仓 `rg "stream_terminated"` 零命中：频道流把它当坏信封（静默重连、无原因），timeline 流因 `event_type != "timeline.entry"` 直接 `continue`。

`qaqh-client` 明确把它归一为 `Transport` 错误以走退避重连（`sse.rs:182-190`）。

### 6.2 修复（已实施）

新增 `STREAM_TERMINATED` 常量与 `stream_terminated_code()`（`runtime.rs:316`、`:319`），在频道与 timeline 两条帧循环中于 `reset_required` **之前**拦截：上报可诊断 `StreamIssue`（含服务端 `code` 与 `skipped`）并触发重连/重定基。

### 6.3 验收清单

```bash
cargo test runtime::tests::termination_frame_forces_channel_reconnect
cargo test runtime::tests::stream_terminated_code_parsing_is_total
# 期望 ok：终止帧返回 false（需重连）、不推进 cursor、错误含 "lagged"；非法载荷退化为 unknown 且不 panic
```

## 9. 不确定性与未验证假设

1. **未取得用户侧的原始报错日志**：`~/.qaqh/qaqh-daemon.log` 在分析期间被截断为 0 字节（`ReadAllBytes` 返回 `bytes=0`），无法给出事故时刻的 `[http]`/`[sse]` 记录。D-1 的因果链由「wire 形状实测 + 代码分支逐行读通」确立（E1+E2），但**未在用户真实事故现场复现**。
2. **未做端到端真机复现**：受限于 D-7（后端 HEAD 编译失败）与「不应干扰用户正在运行的 daemon」，本轮验证止于单元/集成测试与真实 daemon 的 401 探针。
3. **daemon 侧是否也存在同类问题未验证**：`filter_replay_for_session`（`sse.rs:79`）与 `ShardedChannelStream` 的语义正确性依赖 `c1e5a3d` 能否编译，本轮未能运行后端测试。
4. **线上日志为 0 字节的原因未定**：可能是用户清理、也可能日志轮转/写入失败，未进一步排查。
5. D-5 的触发前提是「中间层注入 BOM」，本机直连场景未观测到，保留为推断。
